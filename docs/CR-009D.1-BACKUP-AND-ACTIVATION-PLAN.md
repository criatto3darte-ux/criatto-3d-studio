### 3.2 Como restaurar (procedimento comprovado)

**Rollback rápido (0011/0012 acabaram de ser aplicadas, algo deu errado):**
1. Desativar o Custom Access Token Hook no painel Auth → Hooks.
2. Executar `docs/sql/03-rollback-cr008c-aal.sql` no SQL Editor (service_role). Ele:
   - Verifica que `private.cr009c1_*` existe e é íntegro (senão aborta).
   - DROPa policies afetadas → DROPa as 3 funções → recria funções preexistentes (se houvesse) → recria policies com roles/USING/WITH CHECK originais → REVOKE e re-GRANT de privilégios de tabela/função a partir do snapshot.
   - Valida que o estado final bate com o snapshot (policies, funções, grants) — COMMIT só se tudo bater.
3. Se CLI Supabase foi usado, marcar migrations como revertidas:
   `supabase migration repair 20261114133000 --status reverted --linked`
   `supabase migration repair 20261114133100 --status reverted --linked`
4. Rodar `docs/sql/02-postcheck-verify.sql` para confirmar volta ao estado pré-0011.

**Restauração completa (perda total / projeto corrompido):**
1. Criar novo projeto Supabase.
2. Aplicar migrations 0001–0010 em ordem (o novo projeto já provisiona roles/schemas/auth).
3. Verificar fingerprint (27/27 RLS+FORCE, 38 triggers, 40 policies, 0 JWT funcs).
4. Se a ativação do JWT/AAL também for desejada no novo projeto, seguir as etapas 4–11 da seção 4.

## 5. Procedimento de ativação do Custom Access Token Hook

Após a aplicação da 0011 (que cria `public.custom_access_token_hook` como SECURITY DEFINER com grants para `service_role` e `supabase_auth_admin` **apenas**):

1. Painel Supabase → Authentication → Hooks.
2. Categoria "Custom Access Token" → selecionar hook → ligar.
3. Tipo: **Postgres function** (não HTTP Edge Function).
4. Selecionar a função `public.custom_access_token_hook(jsonb) returns jsonb`.
5. Salvar.

Antes do hook ligado, JWTs emitidos por GoTrue não terão a claim `roles` nem `email_verified` injetados — isso é esperado e é exatamente o estado de pré-ativação validado. Depois de ligar:
- JWT pós-login/senha (AAL1) terá `aal='aal1'` e `roles=[]`.
- JWT pós-MFA TOTP verificado (AAL2) terá `aal='aal2'` e `roles=['proprietario'|'editor'|'operador'|'financeiro']` (conforme registros ativos em `admin_profiles`+`user_roles`).
- A policy `require_aal2()` já adicionada pela 0011 passará a deixar passar somente requisições AAL2.

**Ordem crítica:** a função precisa existir antes do hook ser ligado (a aplicação da 0011 precede a ativação do hook). Desligar o hook é o primeiro passo de qualquer rollback.
